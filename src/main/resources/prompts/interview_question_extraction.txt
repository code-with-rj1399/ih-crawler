<description_rules>
The questionDescription is an ELABORATED VERSION OF questionText.

Its purpose is to explain the SAME question more clearly and completely,
so that a developer can understand what the question is asking without
needing to read the surrounding interview experience.

Think of the fields this way:

questionText:
A concise, faithful statement of the technical question.

questionDescription:
A clearer and more detailed explanation of that SAME technical question,
using only information supported by the source.

The description MUST NOT become a second question, a solution, a related
topic, or a summary of the surrounding interview experience.

<description_scope_rules>
The description MUST stay strictly within the scope of the CURRENT question.

For each extracted question:
1. Identify the exact technical problem represented by questionText.
2. Elaborate only that problem.
3. Use only technical details that belong to that question.
4. Do NOT copy requirements, constraints, examples, inputs, outputs,
   technologies, or details from another question.
5. Do NOT merge neighboring questions into the current question.
6. Do NOT make the current question broader because another question
   appears nearby in the source.
7. Do NOT make the current question more specific using details from
   another question.

Each questionDescription has its own evidence boundary.

Question A must be described from Question A's evidence.
Question B must be described from Question B's evidence.

Do not let Question A's inputs, constraints, examples, or solution
details leak into Question B, and do not let Question B's details leak
into Question A.

The only exception is an explicit cross-reference where the CURRENT
question clearly depends on an earlier part of the SAME supplied source.
In that case, use the standalone cross-reference rules below.
</description_scope_rules>

<description_elaboration_rules>
Elaborate the question naturally.

A good description can clarify:
- What the input/problem is
- What needs to be determined, computed, designed, implemented, or explained
- Important requirements explicitly stated in the source
- Explicit constraints
- Explicit input/output behavior
- Explicit examples
- Explicit edge cases
- Explicit follow-up requirements belonging to the same question

The description should make the question easier to understand, not change
what the question means.

If the source contains a useful example, preserve that source-backed
example when it improves understanding.

If the source does NOT contain an example, do NOT invent one.

"Best examples" means the clearest examples that are actually present in
the supplied source, NOT examples created from general knowledge.
</description_elaboration_rules>

<description_rules_core>
The questionDescription MUST ALWAYS be present.

NEVER return:
- null
- an empty string
- whitespace-only text

The description must describe the TECHNICAL QUESTION OR PROBLEM ITSELF.

It must be written as a standalone problem description that can be shown
directly to a developer or interview candidate without requiring the
surrounding interview experience.

The description should normally be more explanatory than questionText,
but it must remain faithful to the source.

Do NOT artificially add length. A short source question may have a short
description. A detailed source question should have a correspondingly
detailed description.

SOURCE FIDELITY is more important than length.

The description may contain:
- One paragraph
- Multiple paragraphs
- Short sentences
- Multiple related sections when the question has multiple parts
- Explicit follow-up variants
- Explicit constraints
- Explicit examples
- Explicit input/output details
- Explicit edge cases

Choose the structure that best explains the CURRENT question.

Describe the PROBLEM, not the INTERVIEW.

Do NOT describe:
- the candidate
- the interviewer
- the interview process
- how the question was presented
- candidate performance
- what the candidate should do
- what the candidate is expected to know
- why the company asks the question

Avoid phrases such as:
"The candidate is asked..."
"The interviewer asks..."
"The candidate should..."
"This tests..."
"This evaluates..."

Instead, directly describe the technical problem.

The description MAY restate questionText in clearer and more descriptive
language. Restating or clarifying the question is allowed.

However, clarification MUST NOT introduce new technical facts.

The description MUST preserve important technical details explicitly
present in the source, including requirements, constraints, inputs, outputs,
examples, edge cases, follow-ups, and multiple parts of the SAME question.

ONLY include these when they belong to the CURRENT question and are
explicitly supported by the source.

Do NOT import them from another question.
Do NOT invent them.

If the source provides only a short question, keep the description
appropriately short.

If the source provides a detailed problem, provide a detailed description.

If the source provides examples, include the most useful source-backed
examples when they improve understanding.

If the source does not provide examples, do not manufacture examples.

If the source contains multiple related parts of the SAME question,
describe them together logically.

Do NOT split follow-ups into separate questions unless the source clearly
presents them as independent interview questions.

Do NOT provide the solution.

Do NOT add algorithm recommendations, implementation recommendations,
architecture recommendations, code, complexity analysis, or solution
approaches unless those details are explicitly part of the source and
belong to the current question.

The description is a SOURCE-GROUNDED ELABORATION OF THE CURRENT QUESTION,
not a description of the interview and not a synthesis of nearby questions.

<standalone_cross_reference_rules>
A source may describe a technical question as an extension, follow-up,
variant, or continuation of an earlier problem.

The final questionDescription MUST still be understandable on its own.

Remove contextual phrases such as:
- "Using the same grid and moves as the previous problem"
- "Using the same assumptions as above"
- "As in the previous question"
- "With the same input and constraints"
- "Continuing from the earlier problem"
- "Extending the previous problem"

If the CURRENT question explicitly depends on the earlier technical
definition AND that definition is explicitly available in the SAME source,
restate those technical details directly.

If the earlier question is merely another question on the page, do NOT
copy any of its details.

If the referenced earlier problem is not explicitly described in the
supplied source, do not reconstruct it from general knowledge.

Example:

Source:
"The first problem uses a grid with start (0,0), destination (w-1,0),
and allowed moves (x+1,y), (x+1,y+1), and (x+1,y-1). The next problem,
using the same grid and moves, asks for the number of paths that pass
through (a,b)."

Description:
"Determine the number of distinct paths from (0,0) to (w-1,0) using
only the moves (x+1,y), (x+1,y+1), and (x+1,y-1). The path must pass
through the intermediate point (a,b)."

Do NOT output:
"Using the same grid and moves as the previous problem, ..."

</standalone_cross_reference_rules>

QUALITY REQUIREMENT:

Before returning the description, verify:
1. It describes the CURRENT technical problem.
2. It elaborates questionText rather than changing it.
3. It is independently understandable.
4. It contains no details belonging only to another question.
5. It contains no candidate/interviewer/interview-process language.
6. Every technical detail is source-supported.
7. It does not invent requirements, constraints, or examples.
8. It preserves important source-backed requirements and follow-ups.
9. It does not solve the question.
10. It uses useful source-provided examples when available.
11. It does not accidentally merge this question with another question.
12. The structure is natural and readable.
</description_rules_core>

"Find kth largest element."

<confidence_rules>
Assign confidence based ONLY on the evidence present in the source.

0.90 - 1.00:
The source explicitly states the exact technical question/task
with essentially no ambiguity.

0.80 - 0.89:
The source clearly describes the technical question/task with
minor ambiguity.

0.70 - 0.79:
The source clearly indicates a technical interview question/task
but provides limited detail.

Below 0.70:
REJECT the question.

IMPORTANT:

Do NOT automatically assign 1.00 merely because the question
looks like a well-known interview problem.

Confidence must reflect the strength of the SOURCE EVIDENCE.

Do NOT increase confidence because:

- The question is common in interviews.
- The question is a known LeetCode problem.
- The question is technically plausible.
- The company commonly asks such questions.
- The model recognizes the problem.

Confidence must represent source evidence, not general knowledge.

confidence MUST always be between 0.0 and 1.0 inclusive.
</confidence_rules>


<specificity_rules>
questionSpecificity represents how specifically the source describes
the actual technical question.

It MUST always be a number between 0.0 and 1.0 inclusive.

0.90 - 1.00:
The source provides the exact question and important details,
requirements, constraints, examples, or expected behavior.

0.75 - 0.89:
The source provides a clear question with some useful details,
but some aspects are missing.

0.50 - 0.74:
The source provides a recognizable technical question but
very limited detail.

0.00 - 0.49:
The source is too vague to reliably identify the actual question.
Normally reject such a question.

IMPORTANT:

Do NOT increase specificity using general technical knowledge.

Do NOT treat a well-known problem as highly specific merely because
the model recognizes it.

For example:

"Asked LRU cache."
→ lower specificity

"Asked to implement an LRU cache with O(1) get and put operations."
→ higher specificity

Never return values greater than 1.0.

Never return negative values.

questionSpecificity MUST be between 0.0 and 1.0 inclusive.
</specificity_rules>

<experience_title_rules>
The experience.title is a DISPLAY TITLE whose primary purpose is to distinguish this interview experience from other crawled experiences.

Prefer a rich, information-dense title rather than a short generic title. The title may contain as much useful source-supported information as needed to make the experience easy to distinguish from other experiences.

Use a pipe-separated structure and include every useful field that is explicitly supported by the source. There is NO fixed maximum number of title components.

Preferred structure:

ROLE | YOE | LOCATION | COMPANY | ROUND | VERDICT

Possible additional components, when explicitly supported and useful for distinguishing the experience, include:
- interview round
- round number
- interview stage
- verdict / outcome
- offer status
- interview format
- relevant specialization
- internship/full-time status
- experience-specific identifier or role variant
- other concise metadata explicitly stated by the source

Examples:
"Senior Software Engineer | 7 YOE | Bangalore | Google | Onsite | Selected"
"Senior Software Engineer | 5 YOE | Hyderabad | Amazon | Round 2 | Rejected"
"SDE II | 4 YOE | Remote | Microsoft | Phone Screen | Passed"
"Software Engineer (Frontend) | 6 YOE | Pune | OneTrust | Round 2 | Selected"
"SDE Intern | 0 YOE | Bangalore | Amazon | HackOn | Rejected"
"Senior Software Engineer | 8 YOE | Pune | Coupa | Technical Round 2 | Offer Received"

IMPORTANT:
- Include VERDICT/OUTCOME when the source explicitly states it.
- A verdict is factual metadata, not a model judgment. Never invent or infer "Selected", "Rejected", "Offer", "Passed", "Failed", etc.
- If the source explicitly says the candidate was selected, rejected, received an offer, cleared a round, or otherwise states an outcome, that source-supported outcome may be included.
- Preserve useful distinctions such as "Round 2", "Phone Screen", "Onsite", "HackOn", or "Technical Round" when explicitly stated.
- Include the company when explicitly supported by the source.
- Include role, YOE, location, round, and outcome only when explicitly supported.
- Prefer more distinguishing information when it is available.
- Do not omit useful source-supported metadata merely to keep the title short.
- Keep each component concise; do not turn the title into a paragraph or page summary.
- Do not duplicate the same information across components.
- Do not include unsupported information merely because it would make the title more descriptive.

ROLE:
Use the candidate/interview role explicitly stated by the source.

YOE:
Use the candidate's years of experience only when explicitly stated. Preserve useful precision such as "3.5 YOE" when supported.

LOCATION:
Use the interview/candidate location explicitly stated by the source. Do not infer location from company office locations or URL.

ROUND:
Use the interview round/stage only when explicitly stated by the source.

VERDICT:
Use the explicitly stated interview outcome/verdict only when supported by the source. Examples include "Selected", "Rejected", "Passed", "Failed", "Offer Received", or another concise source-supported outcome. Never infer the outcome from the wording, tone, interview performance, or number of questions.

Do NOT:
- invent or infer missing metadata
- infer company from URL, domain, tags, or general knowledge
- infer seniority
- infer location
- infer YOE
