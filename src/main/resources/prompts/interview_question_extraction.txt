<description_rules>
The questionDescription MUST ALWAYS be present.

NEVER return:
- null
- an empty string
- whitespace-only text

The description must describe the TECHNICAL QUESTION OR PROBLEM ITSELF.

It must be written as a standalone problem description that can be
shown directly to a developer or interview candidate without requiring
the surrounding interview experience.

The description may contain:

- One paragraph
- Multiple paragraphs
- Short sentences
- Multiple related sections when the question has multiple parts
- Follow-up variants
- Constraints
- Examples
- Input/output details
- Edge cases

Choose the structure that best represents the source.

Do NOT artificially force the description into a fixed number of
sentences, lines, or paragraphs.

The description should be detailed enough to clearly explain the
question, but SOURCE FIDELITY is more important than length.

IMPORTANT:

Describe the PROBLEM, not the INTERVIEW.

Do NOT describe:

- the candidate
- the interviewer
- the interview process
- how the question was presented
- candidate performance
- what the candidate should do
- what the candidate is expected to know

Avoid phrases such as:

"The candidate is asked..."
"The candidate is told..."
"The interviewer asks..."
"The candidate should..."
"The candidate needs to..."
"The candidate is expected to..."
"This was presented as..."
"This tests..."
"This evaluates..."
"The interviewer wants..."

Instead, directly describe the technical problem.

BAD:

"The candidate is told they start at coordinates (0,0) on a grid
with width w and height h. The candidate should find the number
of paths..."

GOOD:

"Given a grid with width w and height h, the starting position is
(0,0) and the destination is (w-1,0).

From any cell, three moves are allowed:
(x+1,y), (x+1,y+1), and (x+1,y-1).

The task is to determine the total number of distinct paths from
the starting position to the destination using these movement rules.

A secondary variant asks for the number of paths that pass through
a specific point (a,b)."

The GOOD version describes the problem directly.

The description MAY restate questionText in more descriptive language.

Restating or clarifying the question is allowed and is NOT considered
invention.

The description MUST preserve important technical details explicitly
present in the source, including:

- Requirements
- Constraints
- Inputs
- Outputs
- Examples
- Edge cases
- Follow-up questions
- Follow-up variants
- Multiple parts of the problem

ONLY include these when explicitly supported by the source.

Do NOT invent any of these.

If the source provides only a short question, keep the description
appropriately short.

If the source provides a detailed problem, provide a detailed
description.

If the source contains multiple related parts of the same question,
describe them together in a logical structure.

Do NOT split follow-ups into separate questions unless the source
clearly presents them as independent interview questions.

Do NOT provide the solution.

Do NOT add:

- algorithm recommendations
- implementation recommendations
- architecture recommendations
- code
- complexity analysis
- solution approaches

unless those details are explicitly part of the source.

The description is a SOURCE-GROUNDED DESCRIPTION OF THE PROBLEM,
not a DESCRIPTION OF THE INTERVIEW.


<standalone_cross_reference_rules>
A source may describe a technical question as an extension, follow-up,
variant, or continuation of an earlier problem.

The final questionDescription MUST still be understandable on its own.
Do NOT preserve interview-context references such as:

- "Extending the previous problem"
- "As discussed earlier"
- "Continuing from the previous question"
- "Same as above, but..."
- "In the next round"
- "For the follow-up"

Instead, directly describe the technical problem represented by the
current question.

IMPORTANT:

A cross-reference may contain technical information that is necessary
to understand the current problem. Use that information ONLY when the
referenced technical details are explicitly available in the supplied
source content.

For example, if the source explicitly contains:

"Find the number of paths from (0,0) to (W-1,0) using the moves
(x+1,y), (x+1,y+1), and (x+1,y-1). Extending the previous problem,
count the paths that pass through (A,B)."

the description may be normalized to:

"Count the number of distinct paths from (0,0) to the destination
(W-1,0) on a W × H grid using only the moves (x+1,y), (x+1,y+1),
and (x+1,y-1).

The path must pass through the specified intermediate point (A,B)."

The phrase "Extending the previous problem" is removed because it is
interview context, while the explicitly stated grid, destination,
allowed moves, and intermediate point are preserved.

If the referenced earlier problem is NOT explicitly described in the
supplied source, do NOT reconstruct it from general knowledge or from
the model's knowledge of a common interview problem.

In that case:
- describe only the technical information explicitly available for the
  current question;
- do not invent missing constraints or movement rules;
- do not claim details from an unavailable "previous problem";
- remove the cross-reference itself from the final description when it
  does not add technical information that can be independently stated.

A standalone description may use technical details from an earlier
part of the SAME supplied source when those details are clearly part
of the current question's definition. This is source-supported
normalization, not invention.

Do NOT use information from another webpage, another question, external
knowledge, or an assumed earlier interview question to resolve a
cross-reference.
</standalone_cross_reference_rules>

QUALITY REQUIREMENT:

Before returning the description, verify:

1. It describes the technical problem itself.
2. It can be read independently of the interview context.
3. It does not refer to "the candidate".
4. It does not refer to "the interviewer".
5. It does not describe the interview process.
6. It does not describe candidate performance.
7. It does not answer or solve the question.
8. Every technical detail is supported by the source.
9. It does not invent requirements or constraints.
10. It preserves important requirements and follow-ups.
11. The structure is natural and readable.
12. Multiple paragraphs may be used when they improve clarity.
</description_rules>

<duplicate_rules>
Do not return duplicate questions.

Questions should be considered duplicates when they represent
the same underlying interview problem, even if wording differs.

Examples:

"Find the kth largest element."

"Find kth largest element."

These represent the same question and MUST be returned only once.

However, do not merge genuinely different questions merely because
they are related.

When duplicates exist, keep the most faithful representation
of the original source.
</duplicate_rules>


<confidence_rules>
Assign confidence based ONLY on the evidence present in the source.

0.90 - 1.00:
The source explicitly states the exact technical question/task
with essentially no ambiguity.

0.80 - 0.89:
The source clearly describes the technical question/task with
minor ambiguity.

0.70 - 0.79:
The source clearly indicates a technical interview question/task
but provides limited detail.

Below 0.70:
REJECT the question.

IMPORTANT:

Do NOT automatically assign 1.00 merely because the question
looks like a well-known interview problem.

Confidence must reflect the strength of the SOURCE EVIDENCE.

Do NOT increase confidence because:

- The question is common in interviews.
- The question is a known LeetCode problem.
- The question is technically plausible.
- The company commonly asks such questions.
- The model recognizes the problem.

Confidence must represent source evidence, not general knowledge.

confidence MUST always be between 0.0 and 1.0 inclusive.
</confidence_rules>


<specificity_rules>
questionSpecificity represents how specifically the source describes
the actual technical question.

It MUST always be a number between 0.0 and 1.0 inclusive.

0.90 - 1.00:
The source provides the exact question and important details,
requirements, constraints, examples, or expected behavior.

0.75 - 0.89:
The source provides a clear question with some useful details,
but some aspects are missing.

0.50 - 0.74:
The source provides a recognizable technical question but
very limited detail.

0.00 - 0.49:
The source is too vague to reliably identify the actual question.
Normally reject such a question.

IMPORTANT:

Do NOT increase specificity using general technical knowledge.

Do NOT treat a well-known problem as highly specific merely because
the model recognizes it.

For example:

"Asked LRU cache."
→ lower specificity

"Asked to implement an LRU cache with O(1) get and put operations."
→ higher specificity

Never return values greater than 1.0.

Never return negative values.

questionSpecificity MUST be between 0.0 and 1.0 inclusive.
</specificity_rules>
