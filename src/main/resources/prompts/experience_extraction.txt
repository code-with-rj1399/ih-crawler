TITLE

The experience.title MUST follow this exact component order:

ROLE | YOE | LOCATION | COMPANY | ROUND | VERDICT

This is a STRICT FORMAT.

Each component is optional only when the source does not explicitly support it.
Omit unsupported components while preserving the relative order of supported components.

Use exactly " | " as the separator.
Never use another separator between title components.
Never invent a value.
Never use the raw page title if it violates this format.
Never include "Interview Experience" as a generic title component.
Include every supported component.

Component rules:

ROLE
- Use the interview role/position explicitly supported by the source.
- Preserve meaningful seniority such as SDE 1, SDE 2, L3, L4, Senior Software Engineer, Intern, etc.
- Do not invent or normalize away meaningful role information.

YOE
- Include only explicitly stated candidate years of experience.
- Preserve the source's meaningful precision, such as "3 YOE", "3.6 YOE", or "10+ YOE".
- Do not calculate YOE.

LOCATION
- Include the interview/job location only when explicitly stated.
- Preserve the source's meaningful location, such as "Bangalore", "Hyderabad", "India", or "Remote".

COMPANY
- Include the explicitly supported company name.
- Preserve the recognizable company name.
- Do not infer the company from the URL or domain.

ROUND
- Include the relevant interview round/process descriptor when explicitly supported and useful for identifying the experience.
- Examples: "Technical", "DSA", "System Design", "Onsite", "Full Loop", "Phone Screen".
- Do not invent a round.
- If multiple rounds are described but no single concise round descriptor is supported, omit this title component rather than fabricating one.

VERDICT
- Include the explicit interview outcome when supported.
- Normalize obvious equivalent wording to a concise verdict such as "Offer", "Selected", "Rejected", or "Awaiting" only when the source clearly supports it.
- Do not infer a verdict.

Examples of valid title formatting:
- Amazon | SDE 1 | Pune | Offer
- Microsoft | SDE 2 | Hyderabad | Selected
- Google | L3 | Bangalore | Rejected
- Amazon | SDE 2 | 5 YOE | Hyderabad | Amazon | Technical | Offer

Do not add a generic "Interview Experience" suffix or prefix.

If no meaningful supported title components exist, title may be null. Never invent a title.

SUMMARY

Write a concise, factual summary of the interview experience.
The summary should capture the overall experience/process rather than becoming a question list.
When explicitly available, include:
- company
- role
- candidate background/YOE
- major interview rounds
- notable interview process details
- outcome

Do not add facts that are not present in the source.
Do not solve, classify, or elaborate questions in the summary.

POSTED AT

Extract the publication/post date or time when explicitly present in the supplied page content.
Return ISO-8601 when it can be reliably represented that way.
Otherwise null.
Do not confuse the publication date with the interview date.

AUTHOR

Extract the author when explicitly present in the supplied page content.
Otherwise null.
Do not infer an author's identity.

COMPANY

Extract only when explicitly supported by the source.
Do not infer from URL, domain, page title, tags, or outside knowledge.

ROLE

Extract the role/position being interviewed for when explicitly stated.

LEVEL

Extract seniority/level when explicitly stated.
Do not infer it from role unless the source explicitly states it.

LOCATION

Extract interview/job location when explicitly stated.
Otherwise null.

CANDIDATE YOE

Extract years of experience only when explicitly stated.
Do not infer or calculate it.

OUTCOME

Extract the explicitly stated result/outcome.
Examples include Selected, Rejected, Offer, Awaiting, or equivalent source-supported wording.
Do not infer an outcome.

ROUNDS

Extract interview rounds explicitly described in the source.
Preserve their order.
Use concise round names/descriptions.
Do not invent rounds.

<question_evidence_rule>
Every question candidate MUST have explicit supporting evidence in the supplied source.

The source must indicate that the interviewer actually asked, presented, assigned, or required the question/task.

Do NOT infer questions from:

- skills
- resume items
- project descriptions
- job requirements
- topics mentioned in passing
- tools

<question_fidelity>
Preserve original technical meaning and granularity.
Normalize wording only when doing so does NOT change meaning or granularity.

Examples:
"Asked to implement LRU." → "Implement an LRU cache."
"They asked me to find the longest substring without repeating characters." → "Find the longest substring without repeating characters."
"Asked to design a URL shortener." → "Design a URL shortener."

Do NOT add:
- algorithms
- data structures
- constraints
- input/output assumptions
- complexity requirements
- scale
- traffic
- availability requirements
- APIs
- architecture components
- technologies
- follow-up questions

unless explicitly stated in the source.

Never make a question more sophisticated than the source.
Never solve the question.
</question_fidelity>

<question_boundary>
Only extract a question/task when the source indicates that it was actually presented during the interview.

Do NOT convert a topic into a question.
Do NOT convert an answer into a question.
Do NOT convert a candidate's project description into a technical question.
Do NOT convert a round name into a question.
Do NOT create a canonical problem from a vague reference.

Example:
"Round 1 had two tree questions."
Do not invent the names of the two questions.

Example:
"I was asked about Kafka."
Do not expand this into a specific Kafka question that the source does not provide.

If the source only provides a vague question reference, preserve the source wording rather than inventing details.
</question_boundary>

<short_questions>
Short questions are valid when the source clearly indicates that they were asked.
Examples:
- "Kafka?"
- "Why Kafka?"
- "Explain the event loop."
- "LRU cache."

Do not reject or expand a question merely because it is short.
</short_questions>

<contextual_questions>
If a question depends on immediately preceding source text, include enough source wording to preserve its meaning.
Do not invent missing details.
Do not merge unrelated questions.
Only use nearby context when the source clearly establishes that the context belongs to the same question/task.
</contextual_questions>

<duplicate_rules>
Do not return duplicate questions.
Questions representing the same underlying interview problem should appear only once, even if repeated with slightly different wording.
Keep the most faithful source-supported representation.
Do not merge genuinely different questions merely because they are related.
</duplicate_rules>

<order_rules>
Preserve the order in which questions/tasks appeared in the interview experience.
For duplicate questions, preserve the first occurrence's position.
</order_rules>
